## Inputs missing, stubbed or substituted

1. **Live HumanMine model.** humanmine.org was unreachable: curl got 502 from the proxy, and
   `make-inputs.sh` printed WARNING and kept the existing copy. `in/humanmine_model.{xml,json}` are
   **Gos's host copies** (xml md5 ade595cd...), placed in `in/` before the clean run. They were not
   fetched live.
   - Attempt 1's phase 3 ran without them.
   - The clean run's phase 3 onward used them.
   - `rdfc2im project` uses the live model only to decide which core fields to carry into the
     additions.
2. **Gene-symbol resolution needs rdfportal.org even with `--use-cached-data`.** This one blocked
   the build. `translate --genes` resolves the panel's symbols to NCBI/Ensembl ids with a live
   SPARQL query (`scope.py`). The cache covers only `fetch`. Attempt 1 died in
   `translate --source ncbigene` with `resolve_ncbigene_symbols: URLError: Tunnel connection
   failed: 502 Bad Gateway`.
   - Fixed by commit 4cc0b44: an opt-in `RDFC2IM_RESOLVER_CACHE` directory.
   - The two answers were derived from the cached raw data:
     - ncbigene `main.tsv`: 113 ids, whose labels are exactly the 113 panel symbols;
     - ensembl `main.tsv`: 112 distinct ids, because GSTT1 has no Ensembl label.
   - The ids only shape the query text. Items come from the restored raw data, and the final
     counts match BUILD.md.
3. **Hosts that were blocked and are needed:**
   - `rdfportal.org` (symbol resolution, and any fresh fetch);
   - `www.humanmine.org` (the live model);
   - `cdn.jsdelivr.net` and `cdn.intermine.org` (BlueGenes page scripts; jsdelivr returns
     "Approval required").
4. The cache also holds `bluegenes-tools/` and `grch38-chromosome-lengths/`. rdfc2im `main` does
   not use either, so they were ignored. They probably belong to a later rdfc2im branch.

## Failures and workarounds

- **The JDK 8 home directory is not `$HOME`.** To keep this build from touching the shared
  `~/.gradle`, `~/.m2` and `~/.intermine`, the run sets `HOME` to an isolated directory. JDK 8 takes
  `user.home` from the passwd entry, not from `$HOME`.
  - In attempt 1, Gradle therefore used the shared `/home/agent/.gradle` and ignored the 4 GB jvmargs
    written to `$HOME/.gradle`.
  - It also installed `bio-source-humanmine-items:4.3.0` and `bio-source-reactome:5.0.8` into the
    shared `/home/agent/.m2`.
  - The InterMine plugin did read `$HOME/.intermine`.
  - Cleanup: both stray artefacts were removed from the shared `.m2`, and
    `bio-source-reactome/maven-metadata-local.xml` was restored to list only 5.1.1.
  - Fix for the clean run: `JAVA_TOOL_OPTIONS+=" -Duser.home=$HOME"` and
    `GRADLE_USER_HOME=$HOME/.gradle`. This needs no script edit.
- **Moving to the host-mount layout.** Attempt 1 was stopped during integrate because the
  orchestrator asked for data on the host mount.
  - TRIAL_HOME was moved to `repos/.sandbox-disk/rdfc2im/trial_home`.
  - Compose volumes became bind mounts with no compose-file change: before `up`, the named volumes
    were pre-created as `docker volume create --driver local --opt type=none --opt o=bind --opt
    device=<dir> rdfc2im-pgdata` (and the same for `rdfc2im-solrdata`).
  - Compose warns that the volume "already exists but was not created by Docker Compose", and then
    uses it.
  - Postgres 14 ran on virtiofs without problems, and `initdb` was tested first.
- **Running the phases as `--only` steps.** Each phase got its own `RUN_ID`, because every
  invocation truncates its run's timing.tsv. Per-phase logs are under
  `.build-logs/build-im-rkn5-<phase>.log` in the worktree.

## What epic G (build against local intermine artefacts) needs

- **Versions.** The humanmine checkout pins `systemProp.imVersion=5.0.+` and `bioVersion=5.0.+` in
  `gradle.properties`, while our builds publish 5.1.1. The script must override these, or rewrite
  them in `prepare_mine_checkout`. It is not yet checked whether `-DimVersion` beats a systemProp
  in gradle.properties.
- **The reactome source build.** `_install_reactome_jar` hard-codes `version = '5.0.8'`,
  `bio-core/bio-model 5.0.8` and `intermine-integrate 5.0.+`, and resolves the project.xml source
  at `bioVersion`. All of these must follow the local version.
- **Where artefacts come from.** Resolution uses `mavenLocal()`, which is first in humanmine's
  repositories, with `user.home` coming from passwd. A `--intermine-src` flag should publish the
  worktree to a private repo, or pass `-Duser.home`/`maven.repo.local`, so that local artefacts are
  used deliberately and never picked up by accident from the shared `~/.m2`. The shared repo
  already holds 5.1.1 artefacts from the gates.
- **Upstream intermine checkout.** `UPSTREAM_CACHE/intermine` (cloned from intermine/intermine
  HEAD, 787f779, 2026-11-12) supplies the reactome source and
  `default.intermine.production.properties`. For G it should be pointed at the intermine worktree.
- **The webapp.** The war comes from the `intermine-webapp` classes jar and the bio-webapp war at
  `imVersion`, through `unwarBioWebApp`. Both are covered by the version and repository change
  above.
- **The humanmine checkout itself** is intermine/humanmine at 2022-02-23 (afdd8e9), with Gradle 4.9
  and dead JCenter and EBI repositories in `build.gradle`. A 5.1.1 plugin may need a newer Gradle
  wrapper for the mine.
